# tw-stock-analysis 專案分析報告與解決方案

> 分析基準：129 個 py 檔 / 31,337 行 / 21 模組；28 測試檔 / 139 測試；~65 MongoDB 集合。
> 實測工具：pytest 8.4、ruff 0.15、pip-audit 2.10（本機 Windows / Python 3.13）。
> 方法：靜態度量 + 唯讀架構審查（未修改任何原始碼）。

---

## 一、專案概觀

| 面向 | 現況 |
|---|---|
| 定位 | 台股智能分析平台：多因子選股、技術/型態分析、估值、風控、MoE 多模型 AI、LINE 通知 |
| 技術棧 | Python 3.11+、FastAPI、Streamlit、MongoDB(~65 集合)、Ollama LLM、FinMind |
| 規模 | 31,337 行 / 129 檔，最大單檔 843 行 |
| 測試 | 139 測試（但本機因缺 scipy 有 1 收集錯誤） |
| 成熟點 | 計算邏輯、MoE 失效意識、DDD repository 抽象**已存在** |
| 主要痛點 | **基礎設施層**：設定分散、資料存取未收斂、部署綁死單機 |

**核心判斷**：這是一個「**計算層成熟、基礎設施層負債**」的專案。技術債集中在後補未回填的架構層（設定/資料存取/部署耦合），而非業務邏輯。優先修基礎設施可連帶降低其他負債的修復成本。

---

## 二、關鍵問題（依嚴重度）

### 🔴 P0-A：無設定中心，490 處硬編碼 IP/路徑
- **現況**：全樹**無 `config` 模組**；`/home/mdsadmin/Stock/...` 絕對路徑、`172.16.9.27:11434` Ollama IP、`localhost:27017` Mongo 散落 490 處。
- **根因**：環境值以「就地預設參數」擴散，一半用 `os.getenv`、一半裸常數，慣例分裂。
- **影響**：部署綁死單機、無法多環境（dev/stg/prod）、祕密散落、Windows↔Linux 不可攜。
- **佐證**：`analysis/tech_lines.py:12,68`、`moe/router.py:74,138`、`portfolio/lots.py:29`。

### 🔴 P0-B：DB 存取未走既有 repository，43 處裸 `MongoClient`
- **現況**：`domain/repositories/` **已有正確的 `StockRepository`(ABC) + `MongoStockRepository`**，但幾乎無人使用；各類別在 `__init__` 各開連線，無連線池/單例；65 集合名以裸字串散寫。
- **根因**：抽象層後補，既有程式未回填遷移；無 lint/review 約束強制走存取層。
- **影響**：無連線池、schema 無單一真相源、難測試、難抽換底層。

### 🔴 P0-C：MoE 靜默降級，失敗回應污染決策
- **現況**：角色呼叫失敗回「分析失敗:…」字串，**仍被整合與合議採用**；委員連線失敗靜默棄權（三人變兩人）。曾出現 18.8% 失敗率、100% 棄權。
- **根因**：MoE 由多次實驗迭代堆疊，「錯誤訊息當意見」的資料流未阻斷。
- **影響**：**直接污染投資判斷正確性**，且流程全綠難以察覺——這是最危險的一項。

### 🟠 P1-A：上帝模組（4000+ 行混 IO/CLI/計算）
- `strategy/integrated_strategy_v21.py`(632 行檔，模組 4341 行)、`senvision/scanner.py`、`downloaders/download_coordinator.py` 各自把選股/評分/出場/CLI/`MongoClient` 全塞一處。
- **影響**：難測試、改動半徑大。

### 🟠 P1-B：匯入根混亂 + 雙路由器重疊 + 假 GPUManager
- 36 處 `sys.path.insert` 自建套件根、絕對/相對匯入混用；`router.py`(關鍵字路由) 與 `role_router.py`(角色路由) 兩套並存；`GPUManager.loaded` 僅行程內字典、不與實際 GPU 同步。

### 🟡 P2：程式品質與資安
- **ruff 121 錯誤**：E701/E702(複合語句 46)、E402(匯入位置 27)、E741(易混淆變數名 26)、F841(未用變數 11)、F401(未用匯入 6)。
- **資安**（前次稽核）：外部 RSS 標題顯示 **XSS(CWE-79)**、LLM **提示注入(CWE-77/94)**、**SSRF(CWE-918)**、CVE `ipython PYSEC-2023-17`(低影響傳遞相依)。
- **正面**：無 bare `except:`（146 處 except 皆具型別）、TODO/FIXME 僅 3 處。

## 四、解決方案（分階段路線圖）

### 🚀 Phase 0：止血（1–2 週，低風險高回報）
**目標：不改業務邏輯，先擋住「正確性」與「安全」漏洞。**
1. **MoE 守門（P0-C）**：在 advisor/consensus 入口硬性攔截——失敗回應**不計入有效票**、降級須顯式標記。補一條測試「注入失敗回應→確認不進 `tally`/整合」。→ 8h
2. **資安 P0**：外部 RSS 標題純文字化防 XSS；LLM prompt 指令隔離 + `EvidenceGuard` 輸出過濾；Ollama 主機白名單防 SSRF。→ 8h
3. **CI 加護欄**：`ruff check` + `pip-audit` 納入 CI，禁止新增裸 IP/絕對路徑（自訂 grep gate）。→ 4h

### 🏗️ Phase 1：設定收斂（2–3 週）
**目標：解除單機綁定，可多環境部署。**
1. 新增 `src/config.py`（pydantic-settings 或純 `os.getenv` 集中）：MongoDB URI/DB、Ollama 節點表、路徑、API token 全部收斂。→ 8h
2. 分批把 490 硬編碼改為讀設定；`router.py` IP 走 env，統一設定慣例。→ 12h
3. 移除 36 處 `sys.path.insert`，套件化為統一 `src.*` 絕對匯入。→ 8h
4. **驗收**：`grep` 裸 IP/絕對路徑 = 0；139 測試回歸綠。

### 🗄️ Phase 2：資料存取層收斂（3–5 週）
**目標：單一 DB 入口、連線池、schema 真相源。**
1. `MongoStockRepository` 升為唯一入口 + 連線單例（DB/URI 來自設定）。→ 8h
2. 65 集合名收斂到 `collections.py` 常數/schema 模組。→ 8h
3. 分批將 43 處裸 `MongoClient` 改注入 repository（每批以測試回歸）。→ 24h
4. lint 規則禁止直接 `MongoClient`。

### 🧩 Phase 3：模組解耦（4–6 週，選做）
1. 4 個上帝模組抽薄殼：CLI/IO 與計算核心分離，核心純函式化。→ 32h
2. MoE 雙路由合併為單一入口 + 模型→節點對照走設定；GPUManager 改真實查詢或移除。→ 12h
3. 清 121 ruff 錯誤（E741 變數改名、F841/F401 清理）。→ 8h

## 五、建議執行順序與里程碑

```
Week 1-2   Phase 0 止血      → MoE 守門 + 資安P0 + CI護欄        [正確性/安全達標]
Week 3-5   Phase 1 設定收斂  → config.py + 去硬編碼 + 套件化      [多環境可部署]
Week 6-10  Phase 2 資料層    → repository 單一入口 + 集合常數化    [可測/可換底層]
Week 11+   Phase 3 解耦(選做)→ 拆上帝模組 + MoE 統一 + 清 lint    [長期可維護]
```

**最窄驗證路徑**：每階段先以現有 139 測試回歸；Phase 0 的 MoE 守門補 1 條單元測試即可證明「守門有效且不破壞週跑流程」。

**投報比排序**：Phase 0（8+8+4=20h）以最低成本消除最高風險（決策正確性 + 安全），**強烈建議優先**。Phase 1 是後續所有改善的地基。

---

## 六、風險與注意事項
- **不要一次大重構**：所有遷移分批 + 測試回歸，避免破壞已成熟的計算邏輯。
- **本機環境限制**：Windows 缺 scipy/streamlit/ollama，完整回歸需在 Linux 部署環境執行。
- **保留設計資產**：`domain/repositories/` 的 DDD 抽象、MoE 的失效意識（大量實測註解）是專案資產，方案是「回填使用」而非「重寫」。
