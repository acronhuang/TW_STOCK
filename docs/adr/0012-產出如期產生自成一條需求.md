# 「對外產出是否如期產生」自成一條需求（FR-OUT-001），與輸入端資料新鮮度分開

盤點 `data_freshness_audit` 的涵蓋範圍：納管 38 個 collection、豁免 36 個，
**其中屬於「對外產出」的只有 `team_analysis` 一個**，其餘 37 個全是原始資料。

| 產出 | 使用者看到的東西 | 檢查涵蓋 |
|---|---|---|
| `team_analysis` | 團隊合議定案 | ✅ 納管 |
| `verdict_detail` | 判斷準確度逐筆 | 🔴 無 |
| `verdict_performance` | 判斷準確度快照 | ⚪ 豁免 |
| `core_watchlist` | 核心池每日追蹤 | ⚪ 豁免 |

也就是說，監控在盯「資料有沒有進來」，幾乎不盯「產出有沒有出去」。
這一層失效的特徵是**完全靜默**：頁面照常顯示、API 照常回應，只是內容是舊的。

決定：新增 **FR-OUT-001 —— 所有登記在案的對外產出，其最新資料日不得落後預期節奏**。
沿用 `data_freshness_audit` 已有的機制（含「預設納管、豁免須寫理由」），
但**分成兩個需求編號、兩張清單**：輸入端資料新鮮度、產出端如期產生。

## Considered Options

- **(a) 每個產出各一條需求。** 過於細碎——檢查邏輯都一樣（最新資料日 vs 預期節奏），
  差別只在參數。
- **(b) 一條通用需求 + 一張產出清單（採用）。**
- **(c) 直接併入既有的 `data_freshness_audit`。** 會讓「原始資料遲到」與「產出沒生出來」
  混在同一個檢查裡，而兩者的嚴重性與處理方式完全不同：前者通常是上游 API 的問題、
  等一下就好；後者是自己的排程壞了，且會靜默污染所有下游判斷。

## Consequences

- **「預期節奏」必須是清單上的明確參數，不能靠目視判斷。** 各產出的節奏本就不同：
  `team_analysis` 每日、`core_watchlist` 每日、`verdict_detail` 平日**且天生落後一個前瞻視窗**。
- 一個具體的誤判實例（2026-08-16）：`verdict_detail` 最新分析日為 08-06，
  目視「與今天差 10 天」而誤判為嚴重落後；實際上 window=5 需要分析日之後有 5 個交易日，
  理論最新值為 08-07，**只落後 1 個分析日、在容許範圍內**。
  同時誤判其每日 cron「從未執行」為失效——實則該 cron 於週六加入、排程為平日，
  首次執行本就在週一。兩個誤判都源於缺少「預期節奏」這個寫下來的參數。
