# 需求的「當前狀態」與「告警」分離：狀態覆寫，告警只記錄狀態轉變

[ADR-0001](0001-需求即可執行的檢查.md) 把需求定義為「會回傳通過／未通過的可執行檢查」，
但檢查結果目前只寫進 `schedule_alerts`——那是**事件流**不是**狀態**。實測結果：

```
schedule_alerts 總計 152 則 / 未解決 152 則 / 曾被標記為已解決 0 則
最舊未解決 2026-08-01 01:12，最新 2026-08-16 06:00
```

`resolved` 欄位存在但**從未被設為 True**，實務上這是一個唯附加的串流。
具體後果：2026-08-15 已修復的 FinMind 402 問題，其產生的 130 則告警仍掛在「未解決」，
任何人打開該頁看到的 152 則裡，絕大多數是已不存在的問題。

決定：
1. 每支檢查把**當前狀態**（通過／未通過／無資料）寫入 `requirement_status`，
   **以需求編號為鍵覆寫**。
2. `schedule_alerts` 只在**狀態轉變時**寫入一則（綠轉紅、紅轉綠）。

## Considered Options

- **(a) 沿用 `schedule_alerts` 並補上 resolved 機制。** 需要有人手動關閉；
  過去 15 天內 152 則從未有任何一則被關閉，沒有理由相信未來會發生。
- **(b) 狀態與告警分離（採用）。**
- **(c) 只保留狀態、取消告警。** 過於激進：部分狀態轉變應主動通知，而非等人去看板發現。

## Consequences

- 「NFR-QUAL-001 現在通過嗎」問的是**狀態**（覆寫）；「它何時由綠轉紅」問的是**事件**（附加）。
  目前把後者當前者用，所以前一個問題答不出來。
- 告警量會自然下降。FinMind 402 累積 130 則的原因是每次檢查失敗都寫一則；
  改為只在轉變時寫，同一個持續存在的問題只會有 1 則。
  這比 2026-08-15 加的「12 小時去重窗」更根本。
- **紅轉綠也是事件**：目前沒有任何機制記錄「問題已修復」，這正是 152 則全部掛著的原因。
- **現有 152 則告警將作廢**：它們沒有 resolved 狀態、也沒有對應的需求編號，無法遷移。
  保留原表作為歷史紀錄，新機制另起，不回頭補標記。
