# 需求以「可執行的檢查」為載體，門檻變更須留 ADR

本專案的 README 早已宣告 `FR-<模組>-NNN`／`NFR-<領域>-NNN`／`ADR-NNN` 的文件編號規範，
但實際掃描的結果是 FR 文件 0 份、NFR 文件 0 份、ADR 0 份，README 指向的
`專案需求説明/` 目錄在 repo 與 .166 上都不存在。全專案唯一存在的需求編號
`NFR-QUAL-001`，只以兩個 Python 常數（`QUAL_HIT` / `QUAL_EXCESS`）與一段 docstring 的形式存在。

決定：**需求的載體是「一支會回傳通過／未通過的可執行檢查」，而不是一份文件。**
門檻值仍寫在程式碼裡（它必須可執行），但**變更門檻或變更判準的語意，必須留下 ADR**。

## Considered Options

- **(a) 維持現況——需求只活在程式碼常數裡。** 可執行，但無人審查。實例：2026-08-15
  `NFR-QUAL-001` 的命中率基準由「絕對漲跌」改為「超額」，gate 因此由未達標轉為達標，
  全程只需一次 commit，沒有任何機制要求說明或審查。
- **(b) 文件為主、程式碼引用。** 本專案已有反證：`docs/架構規劃/架構四面向詳解-2-架構特性.md`
  記載「團隊分析 ~19h」，2026-08-15 實測為 9.5 天，差 12 倍。該文件同時把品質特性寫成
  1~5 主觀評分，全篇僅 2 行含數字門檻——文件形式的品質標準會與現實分岔且無人察覺。
- **(c) 需求即可執行的檢查（採用）。**

## Consequences

- 專案**已有**整套執行機構，不需新建：`schema_contract_audit`、`data_freshness_audit`、
  `role_failure_watch`、`committee_live_check`、`twse_openapi_sync --check-only`、
  `verdict_orthogonality_backtest`。缺的不是檢查，而是這些檢查沒有對應到任何一條被寫下來
  的需求，且其門檻可被靜默修改。
- 落地只需兩件事：給每支檢查一個需求編號；以及「動門檻或動判準語意要留 ADR」這條規則。
- 隨之而來的問題是：一支「結構上不可能失敗」的檢查，掛上需求編號後會比沒有需求更危險
  （它會持續回報通過）。因此需要另行定義「一支檢查要滿足什麼條件才算數」——見後續 ADR。
