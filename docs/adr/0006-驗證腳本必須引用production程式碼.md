# 驗證腳本一律 import production 函式，禁止重新實作邏輯

2026-08-15 一個工作階段內發生 5 次「測試通過、上線失敗」，模式完全相同：

| 缺陷 | 後果 | 測試為何沒抓到 |
|---|---|---|
| 流動性過濾漏日期上界 | phase1 一啟動即結束（universe 被清為 0） | 獨立測試腳本寫了 `d <= "2026-08-14"`，production 版漏了 |
| 總經快取只換股號未換股名 | 2303 聯電被寫成台積電，顧問整合讀到 | 測試只驗股號，未驗股名 |
| phase3 以空值覆蓋 phase2 的 advisor | 8 檔合議定案全滅，日誌全綠 | 改了 phase2 不寫 JSON，未查誰仍在讀 JSON |
| CRLF 檢查用錯 shell 語法 | 誤報，差點誤判部署有問題 | 檢查方法本身未被驗證 |
| 快取命中率正規表示式吃不到巢狀括號 | 報 0%（實際 92%） | 同上 |

五次中有四次，**測試腳本與 production 的差異本身就是缺陷**——用一份「應該長這樣」的邏輯
去測「實際長這樣」的程式，兩者不一致時測試會通過而 production 會壞。

決定：
1. 驗證腳本一律 `import` production 函式，**禁止重新實作被驗證的邏輯**。
2. 無法 import 者（shell 腳本）一律走 git 部署後在目標機測試，**不 `scp` 暫存版**
   （`scp` 版與部署版的差異同屬上述缺陷類別；且 Windows 工作區的 CRLF 會經 `scp`
   帶入而破壞 shell 腳本）。

## Consequences

- 這條規則承接 [ADR-0002](0002-檢查的有效性條件.md) 第 4 條「檢查本身要能被驗證」：
  一個重新實作 production 邏輯的驗證腳本，驗的是它自己而不是 production，
  **結構上無法發現「production 與我的理解不一致」這一類缺陷**——而那正是上述四次事故的類別。
- 成本接近零：不需新工具、不需他人配合。
- 明確不採用的替代方案：加一層 code review。在單人工作階段中沒有第二位審查者，
  該控制在實務上等於不存在。「下次會注意」亦不採計為控制項——上述五次事故中，
  第二次發生時第一次的教訓已經存在。
