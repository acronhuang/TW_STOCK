# 通知只在需求狀態轉變時發出，另加每週一行摘要防止長期紅燈被遺忘

[ADR-0009](0009-需求狀態與告警分離.md) 建立了「檢查 → 狀態 → 告警」這條鏈，
但沒有定義**人在哪裡進來**。實測顯示這個環節目前是壞的：

| 事實 | 意義 |
|---|---|
| 152 則告警、0 則曾被關閉 | 沒有人在處理告警 |
| `regression_gate` 紅了兩天無人察覺 | 沒有人在看迴歸閘 |
| `check_crontab_drift` 指出的漂移由本人造成，本人隔天才知道 | 連製造問題的人都沒看到 |

若 `requirement_status` 沒有出口，它會變成第 153 到 165 個沒人看的東西——同一個失敗類別、換一張表。

決定：
1. **只在狀態轉變時推送**（綠轉紅、紅轉綠）。沒有變化就完全安靜。
   這直接對應 ADR-0009 的事件語意：只有事件值得打擾人。
2. **每週一次摘要**，內容一行：「目前 N 條需求未通過，其中 M 條已持續超過 7 天」。

## Consequences

- 告警疲勞自然消失：2026-08-01~08-15 的 FinMind 402 問題累積 130 則，
  在此設計下 14 天只會推一則。
- **純事件推送有盲點**：一條長期紅著的需求不再產生事件，於是被遺忘
  （`regression_gate` 紅兩天即為此例）。週摘要即為此而設——
  持續紅著的東西必須定期重新出現在眼前。
- **推送管道本身需要一條需求**：LINE 月額度曾經用盡，且額度耗盡時是**靜默失敗**。
  一個會靜默失敗的推送管道，違反 [ADR-0002](0002-檢查的有效性條件.md) 第 2 條
  （無資料不得視為通過）——推送失敗必須被偵測，否則整條通知鏈的可靠度是未知數。
