# 測試分為「邏輯」與「世界的事實」兩類，只有前者進迴歸閘

`regression_gate.sh`（每日 06:00 跑 `pytest -m unit`）連續兩天紅燈，失敗的是：

```python
def test_ttm_eps_direct_sum(self, valuation):
    """Scenario: TTM EPS 直接加總 4 季"""
    eps = valuation._get_trailing_eps('2706')
    assert eps > 1.0, f"2706 TTM EPS={eps}，應 > 1.0（4 季加總）"
    assert eps < 5.0
```

測試名稱宣稱要測「TTM EPS 加總 4 季」——那是**邏輯**；但它實際斷言的是
「2706 的 TTM EPS 落在 1.0~5.0 之間」——那是**世界的事實**，會隨每季財報改變。
2706 現為 0.67，這個測試抓到的不是程式缺陷，是該公司獲利下滑，且會每季以同樣方式失敗一次。

真正的後果是**迴歸閘失去意義**：它紅了兩天，而 2026-08-15 整夜改了 8 支程式的期間無人察覺——
紅燈的訊號價值已被稀釋。依 [ADR-0002](0002-檢查的有效性條件.md) 第 1 條，
一支「會失敗但失敗不代表被檢查的東西壞了」的檢查並不合格。

決定：
1. **(b) 斷言恆真的關係而非區間**。本例改為
   `_get_trailing_eps('2706') == sum(最近四季 EPS)`——此關係不論獲利多少都成立，
   且真的在測加總邏輯，即測試名稱宣稱的事。
2. **(c) 分類**：`unit` 標記留給邏輯測試，進迴歸閘；斷言真實數值者改標 `data`，
   移出迴歸閘、另建資料合理性檢查。

## Consequences

- 迴歸閘恢復「紅燈＝程式有問題」的意義。
- `data` 類的斷言仍有價值（財報數字異常確實該被發現），但它屬於資料品質檢查，
  應依 [ADR-0001](0001-需求即可執行的檢查.md) 另掛需求編號，而非混進程式碼迴歸。
- 掃描結果：135 個測試函式中有 **16 個**同時使用真實股號與數值區間斷言，分三類：
  1. **可改為恆真關係**（`test_ttm_eps_direct_sum`、`test_dupont_roe`、`test_rsi_range`）——
     改寫後與世界脫鉤，且測得比原本更準。
  2. **確為世界事實**（`test_tsmc_grade_A`、`test_pe_band_max_25`、`test_warnings_for_weak_stock`）——
     斷言「這家公司現在的狀況」，移出迴歸閘。
  3. **僅以真實股號為夾具**（`test_2330_has_price`、`test_analyze_2330`）——斷言「有資料/有結果」，
     實質是資料檢查而非程式檢查。
- **分兩批處理**：第一批只修「已失敗或即將失敗」的，第二批處理其餘。

### 第一批的範圍修正（2026-08-16）

原訂第一批為上述四支，但那**全部標記為 `integration`，不在迴歸閘（`pytest -m unit`）
範圍內**，修它們不會讓閘門變綠。閘門紅燈的真正原因是
`TestCorePool.test_latest_buys_picks_full_market_not_latest_daily`——
2026-08-15 在 `latest_buys()` 加入反動能過濾後，該函式開始查 `db.stock_price`，
而測試的 `_FakeDB2` 只提供 `team_analysis`，於是 `AttributeError`。
**是加了新的資料相依卻沒更新假物件，不是測試斷言了世界的事實。**

第一批因此改為修這一支，並補上反動能過濾當初缺的覆蓋（排除漲最多／保留缺資料者）。
完成後 `pytest -m unit` 為 29 passed / 0 failed。原訂那四支移入第二批。

### 待查：迴歸閘的實際覆蓋範圍

`pytest -m unit` 只選中 143 支中的 **29 支**，**114 支被 deselect**。
若那 114 支裡有真正的邏輯測試被誤標為 `integration`，
閘門的保護範圍會比想像中小很多。需逐支檢視標記是否合理——屬第二批工作。
