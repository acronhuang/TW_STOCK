## 可失敗性證據（已寫進各支 docstring，可重跑）

```
role_failure_watch      --max 0.001                          -> 1
committee_live_check    CONSENSUS_MODELS 含不存在的模型         -> 1
verdict_orthogonality   QUAL_TARGET_ANNUAL=5.0               -> 1
```

每組皆成對驗證（正常參數必須回 0）——只測反向會把「恆紅」誤判為合格。

## 過程中發現並修復的缺陷

**`verdict_orthogonality_backtest` 的 `main()` 無條件 `return 0`。**
它會印「🔴 未達標」、會寫 `schedule_alerts`，但**結束碼永遠是 0**，
任何以結束碼判斷的呼叫端（cron、`requirement_status`、監控包裝）一律看到「通過」。
成因是 2026-08-15 加入 `--windows` 多視窗時，接住了 `run_one` 的回傳值卻沒使用。

此缺陷**靜態讀碼看不出來**——失敗路徑確實存在（會印、會告警），只是結束碼沒反映它。
這是同一晚第三個「有失敗分支 ≠ 到得了失敗分支」的實例，另兩個為：
`role_failure_watch` 舊版的 `return 1` 因缺新鮮度檢查而永遠走不到；
`NFR-QUAL` 的告警組態剛好避開唯一會失敗的視窗。

## 一個被推翻的預期

審視前預期 `check_crontab_drift` 會有缺陷（擔心刪掉 `deploy/crontab.txt` 就能讓它永遠靜音），
實測結果是它正確回結束碼 2 並明說「找不到快照」。三支的條件 2 全數通過，未發現新問題。

## Consequences

- 這七條需求即為 `requirement_status`（[ADR-0009](0009-需求狀態與告警分離.md)）的初始鍵。

  皆未回寫 `deploy/crontab.txt`。此為真實的漂移，不是誤報。
- 「附一個可重現的失敗指令」成為給編號的常規要求，寫在被檢查腳本的 docstring 裡，
  日後改動可直接重跑驗證。
