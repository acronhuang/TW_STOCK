# 需求編號分四個 NFR 領域 + FR-OUT；「做事順便告警」的程式不給編號

盤點 12 支會寫 `schedule_alerts` 的程式後發現它們性質不同：

| 類型 | 支數 | 成員 |
|---|---|---|
| **真正的檢查**（唯一職責就是判定） | 7 | `regression_gate`、`check_crontab_drift`、`schema_contract_audit`、`data_freshness_audit`、`committee_live_check`、`verdict_orthogonality_backtest`、`role_failure_watch` |
| **做事順便告警** | 5 | `macro_sync`、`twse_market_totals_sync`、`core_watchlist_daily`、`consensus.py`、`team_daily_verified.py` |

決定：沿用 README 既有的 `NFR-<領域>-NNN` / `FR-<模組>-NNN` 規範，分五類：

| 領域 | 涵蓋 | 現有檢查 |
|---|---|---|
| `NFR-QUAL` | 判斷品質 | `verdict_orthogonality_backtest`（001=5 日、002=20 日） |
| `NFR-DATA` | 資料完整性與契約 | `data_freshness_audit`、`schema_contract_audit` |
| `NFR-OPS` | 系統運作正確 | `check_crontab_drift`、`committee_live_check`、`role_failure_watch` |
| `NFR-CODE` | 程式碼迴歸 | `regression_gate` |
| `FR-OUT` | 產出如期產生 | 待建（[ADR-0012](0012-產出如期產生自成一條需求.md)） |

**第二類那 5 支不給編號。** 理由是它們違反 [ADR-0002](0002-檢查的有效性條件.md) 第 1 條的精神：
一支「只有在自己有跑時才會告警」的程式，無法回答「這件事現在正常嗎」——
它不跑就不會說話，而「它沒跑」正是最需要被發現的失效。
它們的健康度應由 `FR-OUT-001` 從**外部**檢查；只有外部觀察者才能發現「它沒跑」。
其現有告警保留（是有用的除錯訊息），但不進 `requirement_status` 看板。

## Consequences

- 分類會讓**空白處自己浮出來**。目前 `FR-` 只有一條（產出如期產生），
  而 FR 是功能需求——這暗示本專案幾乎沒有定義過「它應該做到什麼」，
  只定義了「它不該壞掉」。此空白值得日後單獨處理，本 ADR 不解決。
- 不採用「依壞掉時誰受害分類」：更貼近後果，但與 README 既有規範不符，
  會產生兩套並行的編號習慣。
- 不採用「全部 REQ-NNN 流水號」：最簡單，但失去「這個領域有沒有被涵蓋」的檢視能力。
