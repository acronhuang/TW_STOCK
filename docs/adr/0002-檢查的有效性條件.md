# 一支檢查要滿足四項條件才夠格掛需求編號，其中兩項為硬性門檻

[ADR-0001](0001-需求即可執行的檢查.md) 把「可執行的檢查」定為需求的載體。隨之而來的風險是：
一支**結構上不可能失敗**的檢查，掛上需求編號後會比沒有需求更危險——它會持續回報通過，
而讀的人會以為那代表系統健康。

決定：檢查須滿足以下四條，其中 **1 與 2 為硬性門檻**（不滿足者不得掛需求編號），
3 為設定紀律，4 為盡力而為。

1. **可失敗性（硬性）**——必須能舉出一組具體的真實輸入使它回傳未通過。舉不出來就不是檢查。
2. **無資料 ≠ 通過（硬性）**——輸入為空、來源過期或查無資料時，須回報「無資料」並視為未通過，
   不得回傳通過。監控的語意是「系統現在是否健康」，不是「最後一次看到的數字是多少」。
3. **告警與判定同一組態**——被排程執行且會發出告警的那組參數，必須就是判定用的那組。
   違反時屬設定錯誤，不是檢查本身失效。
4. **已知答案對照組**——檢查本身要能被驗證。有就寫進 docstring，沒有就明說沒有；不強制。

## Consequences

發現時即違反本 ADR 的既有檢查（掛編號前須先修）：

- `scripts/role_failure_watch.py` 違反第 2 條：讀 log 尾端最後 N 檔算失敗率，
  但無任何新鮮度檢查。週跑結束後 log 停止增長，它每小時仍回報同一批舊數字並顯示通過，
  結構上永遠不會響。
- `NFR-QUAL-001` 的排程違反第 3 條：月排程用 20 日視窗且帶 `--alert`（目前 68.6%／+2.18%，通過）；
  每日排程跑 5/10/20 但不帶 `--alert`，而 5 日視窗為 56.2%／+0.71%（不通過）。
  唯一會發告警的組態，剛好是唯一會通過的組態。

第 4 條的既有實例：退化委員偵測以 `hermes3:8b` 的 85.4% 買進率為已知答案，
證明偵測器確實抓得到目標；TWSE 全市場總表同步以 2026-08-14 法人合計買進
511,271,838,131 為錨，對不上即中止不寫。
